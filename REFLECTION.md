# REFLECTION

## 1. What was the hardest bug you faced?
The hardest bug was the "Hobby Plan Savings" logic in the audit engine. Initially, the engine was designed to find the absolute cheapest plan available. Since most tools (Cursor, Claude, ChatGPT) offer a "Free" or "Hobby" tier at $0, the engine was recommending that every single user switch to the free tier to save 100% of their spend. While technically correct for a pure "savings" tool, it was practically useless for a B2B lead-gen tool. A startup with 10 engineers isn't going to switch to the free tier of Cursor; they'd lose all productivity. I had to refactor the engine to respect the "Value Tier." I implemented a check that excludes plans with `priceMonthly === 0` from recommendations if the user is currently on a paid plan. This ensured the savings were realistic—comparing paid tiers to other paid tiers or right-sizing seats within a paid tier—while still allowing for redundancy detection. This required a subtle shift in how I filtered the `PRICING_DATA` array during the iteration loop, ensuring that I only compared plans within a "Productivity Threshold."

## 2. What was a decision you reversed during the build?
I initially planned to use a complex state management library (Zustand) to handle the 3-step audit wizard. I thought the complexity of managing an array of tool entries, each with their own nested properties, would require a centralized store. However, on Day 4, I realized that for a lead-gen tool, persistence was more important than complex state transitions. If a founder spent 5 minutes finding their spend data and then accidentally refreshed the page, losing that data would result in an immediate bounce. I reversed the decision to use Zustand and instead built a custom `useLocalStorage` hook. This allowed me to keep the state local to the wizard component while automatically syncing every keystroke to the browser's storage. This was a "Founder Mindset" decision: prioritizing the user experience and completion rate over "clean" architectural abstractions. It simplified the code and made the app much more robust.

## 3. If you had a second week to build, what would you add?
In the second week, I would focus on "Benchmark Mode." I would collect anonymized spend data from all audits to create a "Spend per Developer" index. This would allow users to see how they compare to other startups of similar size (e.g., "You spend $92/dev/mo on AI, while the average Seed-stage startup spends $45"). This social proof is a powerful psychological trigger for B2B leads. Additionally, I would implement a "One-Click Export" that generates a branded PDF report. While the current shareable URL is great for quick viewing, a PDF is what a CTO or Finance Lead needs to attach to an internal memo or Slack thread to justify a budget cut. Finally, I would add a "Team Invitation" flow where a lead developer could invite their teammates to "verify" their own tool usage, turning the audit from a single-user form into a collaborative verification tool.

## 4. How did you use AI to help you build this?
I used AI as a "Senior Architect" and "Data Researcher." Specifically, I used large language models to aggregate the May 2026 pricing data for the eight core tools, which saved me hours of manual tab-hopping across vendor sites. I also used AI to generate the initial Neo-Brutalist CSS tokens, as it was able to suggest harmonious HSL values for the "Chunky" aesthetic faster than I could manually tweak them in a color picker. For the application logic, I used AI to write the boilerplate for the Vitest test cases, allowing me to focus on the high-level audit rules. In the final product, I integrated **Google Gemini 1.5 Flash (Free Tier)** to provide the personalized summary. This allowed for a zero-cost, high-speed execution flow that is accessible to any developer without a paid API subscription.

## 5. Self-rating (1-10) and Why?
I rate myself an 8.5/10. I successfully built all 6 MVP features within the timeframe, including a robust audit engine with verified math and a highly polished "premium" UI that exceeds typical lead-gen tool standards. The code is modular, type-safe, and fully tested (exceeding the 5-test requirement). I demonstrated a "Founder Mindset" by prioritizing persistence and lead-capture UX over purely technical goals. I lost 1.5 points because I didn't get to implement the "Bonus" PDF export feature, and because the Supabase integration currently relies on environmental variables that the end-user has to provide, rather than a seamless "one-click" setup. However, as a production-ready lead-gen tool for Credex, this is a highly effective piece of engineering that balances aesthetics, logic, and entrepreneurial goals.
