# ROUND2_REFLECTION.md

## 1. What was the most uncomfortable trade-off you made because of the time pressure?
The most uncomfortable trade-off was electing not to create a separate dashboard UI for managing/updating pricing overrides, choosing instead to handle updates strictly via `POST /api/detect-changes`. While this fulfills the requirement and remains fully functional for script-based triggers, it leaves administrative operations less accessible to non-technical users. Additionally, relying on the `/api/leads` step to retrospectively add the user's email to their `audits` record (rather than requiring an email before the audit calculations run) was a product constraint I preserved to protect the low-friction conversion funnel from Round 1. Under less pressure, I would have built a secure admin dashboard page to edit, add, and inspect tool plans directly with visual validation before dishing out notifications to users.

## 2. If we extended the deadline by another 24 hours right now, what's the first thing you'd do?
The single first thing I would do is set up a local SQLite or PostgreSQL client fallback database for local development environments when Supabase is unreachable. Because the backend relies heavily on Supabase for the audits/leads relation, local development and testing are tightly coupled to a live cloud network connection. If the cloud database is offline, the features degrade. Implementing an automated file-based database fallback (like SQLite or simple JSON file storage) for local testing would allow developers to run the entire end-to-end cron detection, email alerts, and diff comparisons offline without setting up external database connections, improving developer experience and code resiliency.

## 3. Looking back at your Round 1 codebase as a now-experienced user of it: what's one thing your Round 1 self made harder for your Round 2 self?
My Round 1 self imported the static `PRICING_DATA` object directly into `runAudit` inside `lib/audit-engine.ts`. This created a hard dependency that assumed pricing data would always be static, singular, and loaded from a local file. For Round 2, because we needed to calculate recommendations comparing a stored snapshot against a set of live overrides, this lack of parameterization forced me to refactor the main calculation engine to accept optional custom pricing snapshots. Had I designed the audit engine in Round 1 with basic dependency injection (passing pricing data as an explicit configuration parameter to the audit executor), extending it to support dynamic recalculations and comparative audits in Round 2 would have been a drop-in change requiring zero modifications to the core engine.
